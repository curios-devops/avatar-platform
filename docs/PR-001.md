PR-001 — MEYA Universal Avatar & Digital Worker Generator

Project: MEYA
Product: Universal Digital Worker Studio
Priority: P0 — Foundational product architecture
Initial worker: AI Influencer & Sales Representative
Implementation: Refactor and extend existing MEYA application
Deliverable: Fully functional visual and conversational Digital Worker Generator
Document type: Product Requirements & Technical Implementation Specification

⸻

1. Product vision

MEYA is a platform for creating, personalizing, deploying and managing digital workers represented by persistent AI avatars.

A user should be able to describe a job in natural language, interact with MEYA’s creation assistant, and obtain a specialized digital worker capable of performing that job.

The user should not need to understand AI models, agents, APIs, prompts, workflows or integrations.

MEYA translates the user’s intentions into a configured digital worker.

A worker combines:

1. Identity — who the worker is.
2. Appearance — what the worker looks and sounds like.
3. Personality — how the worker behaves and communicates.
4. Role — what the worker is responsible for.
5. Skills — what the worker knows how to do.
6. Tools — which applications and services it can use.
7. Memory — what it knows and remembers.
8. Objectives — what results it must achieve.
9. Autonomy — what it can do independently.
10. Reporting — how it communicates progress and results.

The avatar is the human-facing representation of the worker. Its underlying intelligence, memory, capabilities and execution environment must remain independent of the visual representation.

1.1 Product principles

* Conversational first: the user describes what they need rather than filling out technical configuration forms.
* Visual by design: the worker is visible throughout creation and operation.
* Reusable by default: existing workers, identities, configurations and capabilities can be reused.
* Modular architecture: capabilities are composable rather than hardcoded to a particular job.
* Human control: autonomy is configurable and permission-based.
* Persistent identity: workers retain their identity, history and memory between sessions.
* Outcome-oriented: workers are evaluated by results, not by the number of conversations they generate.
* Extensible: new roles, skills, tools and integrations should not require rebuilding the generator.

1.2 First commercial objective

Build our first production-ready worker:

AI Influencer & Sales Representative

This worker should understand a company’s product, represent its brand, develop a social media presence, create marketing content, publish approved posts, interact with its audience where supported, generate leads and measure commercial results.

It should operate as a persistent digital employee, not simply as a video-generation tool.

2. Universal worker architecture

The most important architectural decision in this PR is separating the worker into reusable components.

Do not implement a separate agent architecture for influencers, salespeople, assistants or other professions.

All workers must share the same underlying model.

2.1 Worker composition model

A Digital Worker is assembled from the following components:

A. Identity

Defines who the worker is.

Properties:

* Unique worker ID.
* Display name.
* Short description.
* Avatar identity.
* Visual appearance.
* Voice.
* Language.
* Personality.
* Communication style.
* Professional background.
* Optional public profile.

Identity should be independent of the worker’s job.

The same avatar identity could become a salesperson, customer support representative or educator without losing its visual identity.

B. Role

Defines what the worker does.

Examples:

* Influencer.
* Sales representative.
* Marketing manager.
* Community manager.
* Customer support representative.
* Research assistant.
* Executive assistant.
* Recruiting assistant.
* Teacher.
* Personal assistant.

A role must not be a rigid predefined agent.

It is a structured definition containing:

* Responsibilities.
* Expected outcomes.
* Required skills.
* Recommended tools.
* Typical workflows.
* Performance metrics.
* Knowledge requirements.
* Autonomy recommendations.

Roles should be extensible through configuration.

C. Skills

Skills represent reusable abilities that can be attached to any worker.

Examples:

* Market research.
* Content strategy.
* Copywriting.
* Video scripting.
* Video generation.
* Image generation.
* Social media publishing.
* Lead qualification.
* CRM management.
* Customer communication.
* Sales prospecting.
* Analytics.
* Reporting.

Skills should be independently versioned and reusable.

A skill describes its purpose, inputs, outputs, required permissions, dependencies and execution requirements.

Workers can share skills without sharing private memory.

D. Tools and integrations

Tools allow workers to interact with external systems.

Examples:

* TikTok.
* Instagram.
* YouTube.
* LinkedIn.
* X.
* CRM.
* Email.
* Calendar.
* Website.
* Analytics.
* Product catalog.
* Payment platform.
* Image generation.
* Video generation.
* Voice generation.
* Web search.

A worker should only see and use tools explicitly enabled for it.

Integrations must be abstracted behind a common connector interface, with platform-specific implementations.

E. Memory

Every worker must have persistent memory.

Memory must be logically separated into:

1. Identity memory: facts about the worker and its established personality.
2. User memory: information about the owner and their preferences.
3. Business memory: products, services, customers, brand and business information.
4. Operational memory: previous tasks, decisions and execution history.
5. Learned memory: insights extracted from successful and unsuccessful activities.
6. Episodic memory: relevant interactions and past events.

Memory must be searchable and selectively retrievable.

Do not inject the entire memory into every model request.

Implement retrieval based on relevance and context.

Important: memory must belong to the worker, not to the underlying model or a particular conversation.

F. Objectives

Define what the worker is trying to achieve.

Examples:

* Generate 100 qualified leads per month.
* Publish five videos per week.
* Increase Instagram engagement.
* Generate product demonstrations.
* Respond to customer inquiries within a specified period.

Objectives must support:

* Target value.
* Measurement method.
* Time horizon.
* Priority.
* Current progress.
* Success criteria.

G. Autonomy and permissions

Define what the worker is allowed to do.

Four recommended autonomy levels:

Level 1 — Assistant

* Suggests.
* Researches.
* Creates drafts.
* Waits for instructions.

Level 2 — Supervised

* Executes tasks after individual approval.
* Can prepare content and workflows.
* Requires approval before external actions.

Level 3 — Delegated

* Executes predefined workflows independently.
* Uses configured limits and approval policies.
* Reports exceptions.

Level 4 — Autonomous

* Executes approved objectives continuously.
* Manages schedules and workflows.
* Optimizes activities within defined boundaries.
* Escalates important decisions and exceptions.

The autonomy level must never override individual tool permissions.

Publishing, sending messages, spending money, changing account settings and accessing sensitive information must each have independent permissions.

3. The Universal Worker Generator

The generator is the core of MEYA.

It should allow users to create a new worker through a dynamic combination of conversation and visual interaction.

The experience should feel like creating a digital person and onboarding a new employee.

3.1 Entry point

The user selects:

Create a new Digital Worker

The application opens the Worker Studio.

The user can:

* Describe the worker they want.
* Select a generic role.
* Start from an existing worker.
* Clone an existing worker’s configuration.
* Start from a recommended profile.

Examples:

“I want a salesperson who understands our SaaS product and generates leads.”

“I need an influencer who represents my fashion brand on TikTok and Instagram.”

“I want an assistant to manage my calendar and respond to customer emails.”

“I need someone who researches competitors and prepares weekly reports.”

The generator must interpret these descriptions and create an initial worker configuration.

3.2 Conversational onboarding

MEYA’s creation assistant should behave like an experienced HR manager, product strategist and AI systems architect.

It must understand the user’s intentions and ask only the questions necessary to configure the worker.

It should not present a long static questionnaire.

The process must be adaptive.

Step 1 — Understand the user and business

Determine:

* Is the user an individual, creator, startup or established company?
* What product or service does the business offer?
* Who are its customers?
* What market does it operate in?
* What is its value proposition?
* What problem does it solve?
* What differentiates it?
* What is the worker expected to accomplish?
* What does success look like?

The assistant should ingest existing information whenever possible.

Potential information sources:

* Website URL.
* Uploaded documents.
* Product catalog.
* Company presentation.
* Existing social media accounts.
* Existing marketing materials.
* CRM information, if connected.

Do not ask users to repeat information that can be extracted from supplied sources.

The assistant should create a structured business profile and ask the user to validate important assumptions.

Step 2 — Define the role

The generator should translate the user’s request into a role definition.

For the first worker, the assistant should recognize a combination of:

* AI Influencer.
* Brand Ambassador.
* Content Creator.
* Social Media Manager.
* Sales Representative.

It should recommend which responsibilities belong to the worker and which require external services.

The user must be able to add, remove or modify responsibilities.

The resulting role must be stored as a reusable profile.

Step 3 — Create the identity

The user creates the worker’s identity.

The assistant proposes:

* Name.
* Gender presentation, if desired.
* Approximate age appearance.
* Visual style.
* Professional appearance.
* Clothing.
* Personality.
* Communication style.
* Voice.
* Accent.
* Languages.
* Background story.
* Professional expertise.

The user should be able to create or modify the appearance visually.

The existing MEYA avatar system should be reused.

Do not introduce a new avatar rendering architecture if the current one already supports the required functionality.

The identity should remain consistent across videos, conversations and future interactions.

The system should support identity variants such as:

* Professional.
* Casual.
* Studio.
* Product demonstration.
* Promotional campaign.

Variants must preserve the underlying identity.

Step 4 — Configure personality

The assistant should infer an initial personality from the business and role.

Examples:

* Professional and trustworthy.
* Energetic and persuasive.
* Friendly and approachable.
* Technical and analytical.
* Humorous and entertaining.
* Premium and sophisticated.

The user should be able to modify personality using natural language.

For example:

“Make him more charismatic and funny, but never aggressive when selling.”

Personality should be represented as structured behavioral instructions, not merely a single prompt.

Include:

* Tone.
* Formality.
* Persuasiveness.
* Humor.
* Emotional expression.
* Communication boundaries.
* Sales philosophy.
* Ethical restrictions.
* Brand alignment.

Step 5 — Define knowledge

The worker must learn the business.

The assistant should create an initial knowledge base using:

* Company website.
* Product documentation.
* FAQs.
* Pricing.
* Product catalog.
* Brand guidelines.
* Sales materials.
* Customer profiles.
* Competitor information.

Knowledge must be distinct from memory.

Knowledge is authoritative information supplied or verified by the user.

Memory contains experiences, observations and learned information.

The worker must not invent product features, prices, testimonials or guarantees.

If it does not know something important, it should ask or escalate.

Step 6 — Configure tools

The assistant recommends integrations based on the role.

For the influencer:

* TikTok.
* Instagram.
* YouTube Shorts.
* Video generation.
* Image generation.
* Voice generation.
* Social scheduling.
* Analytics.
* Product catalog.
* CRM.
* Web research.

The user chooses which tools to activate.

Each integration should have:

* Connection status.
* Granted permissions.
* Available capabilities.
* Connection owner.
* Last synchronization.
* Error status.

Never ask users to paste access tokens into chat.

Use OAuth wherever supported.

Step 7 — Configure memory and learning

The assistant proposes what information should persist.

Examples:

* Brand voice.
* Target audience.
* Preferred products.
* Previous campaigns.
* Successful content.
* Customer objections.
* Sales insights.

The user should be able to inspect and correct important learned information.

Step 8 — Define objectives and autonomy

The assistant proposes:

* Goals.
* KPIs.
* Schedule.
* Reporting frequency.
* Autonomy level.
* Approval requirements.
* Escalation conditions.

The user confirms the final configuration.

3.3 Dynamic visual generation

The Worker Studio must update visually while the conversation progresses.

The user should see:

* The avatar taking shape.
* The identity being defined.
* The role and capabilities being assembled.
* Tools being connected.
* Knowledge being loaded.
* Objectives being configured.

This should not feel like a traditional setup wizard.

The visual experience should resemble an interactive workspace where the user is creating and onboarding a digital employee.

4. Worker Profiles and Reusability

This is one of the most important differentiators of MEYA.

We must avoid creating every worker from scratch.

4.1 Generic profiles

Create a flexible library of generic role profiles.

Initial profiles:

1. Influencer.
2. Sales Representative.
3. Marketing Specialist.
4. Community Manager.
5. Customer Support.
6. Researcher.
7. Executive Assistant.
8. Personal Assistant.
9. Educator.
10. Content Creator.

These profiles should be starting points, not independent products.

Each profile contains:

* Default responsibilities.
* Recommended skills.
* Suggested tools.
* Suggested workflows.
* Typical KPIs.
* Recommended memory configuration.
* Suggested autonomy level.

4.2 Worker inheritance and cloning

Users should be able to create a new worker using an existing worker as a starting point.

Example:

The user creates an AI Influencer.

Later, they want a second worker to sell a different product.

Instead of starting from zero, they select:

Create from existing worker.

MEYA should offer reusable components:

* Identity.
* Personality.
* Role.
* Skills.
* Knowledge structure.
* Tool configuration.
* Workflows.
* Objectives.
* Autonomy policies.

The user can choose which components to reuse.

Important distinction:

Cloning a worker must not automatically copy its private memories, conversation history, account credentials or customer data.

The user should explicitly choose whether to reuse selected business knowledge and learned insights.

The new worker receives its own identity ID, memory namespace and execution history.

4.3 Shared capabilities

Several workers may share:

* Brand guidelines.
* Company knowledge.
* Product catalog.
* Approved marketing materials.
* CRM integration.
* Video generation tools.

However, their individual identities, memories and responsibilities remain separate.

Design the system to support future worker teams.

For example:

* Influencer creates demand.
* Sales representative qualifies leads.
* Customer support answers questions.
* Marketing manager coordinates campaigns.

Each worker can collaborate through explicit tasks and shared business resources.

5. Initial worker: AI Influencer & Sales Representative

This is the first fully implemented role.

The worker should have a complete operational lifecycle.

5.1 Mission

Represent a business or product through a consistent digital identity, build an audience, create and distribute content, engage potential customers and contribute to sales.

It must operate continuously according to its configured objectives and permissions.

5.2 Operational responsibilities

A. Understand the business

Build and maintain:

* Business profile.
* Product knowledge.
* Brand guidelines.
* Target audience.
* Buyer personas.
* Value proposition.
* Competitive positioning.
* Marketing objectives.

B. Develop its influencer strategy

Determine:

* Target platforms.
* Audience segments.
* Content pillars.
* Communication style.
* Posting frequency.
* Content formats.
* Campaign strategy.
* Relevant trends.

The worker should recommend a strategy and allow the user to approve or modify it.

C. Manage social accounts

Support connection and management of:

* TikTok.
* Instagram.
* YouTube / Shorts.

Future integrations:

* LinkedIn.
* Facebook.
* X.

The worker should distinguish between:

* Account connection.
* Content upload.
* Draft creation.
* Scheduled publishing.
* Public publishing.
* Comment management.
* Messaging.
* Analytics.

These are separate capabilities, not a single generic permission.

The application must only advertise capabilities actually supported by the connected account and authorized API.

D. Create a content calendar

Generate a dynamic calendar based on:

* Business objectives.
* Campaigns.
* Target audience.
* Content pillars.
* Platform.
* Frequency.
* Product priorities.
* Seasonal events.
* Relevant trends.

Each calendar item should contain:

* Planned date.
* Platform.
* Content format.
* Topic.
* Hook.
* Intended audience.
* Objective.
* Associated product or service.
* Call to action.
* Status.

The user must be able to edit the calendar visually.

E. Generate content

The worker should be capable of producing:

* Short-form videos.
* UGC videos.
* Product demonstrations.
* Educational content.
* Promotional videos.
* Testimonials, only when genuine and authorized.
* Product comparisons.
* Stories.
* Images.
* Carousels.
* Captions.
* Hashtags.
* Calls to action.

The worker should use MEYA’s existing avatar and media generation capabilities.

The same content should be adaptable to different platforms rather than simply duplicated.

Example:

One product campaign can produce:

* A TikTok video.
* An Instagram Reel.
* A YouTube Short.
* A supporting image.
* A caption for each platform.

The worker must respect the format, duration and content requirements of each destination.

F. Associate content with commercial objectives

Content should not be generated independently of the business.

Every promotional content item should optionally associate with:

* Product.
* Service.
* Campaign.
* Landing page.
* Affiliate link.
* Promotion.
* Lead-generation objective.

The system should track which content is associated with which commercial outcome.

G. Review and approval

Provide an approval workflow.

Content states:

* Idea.
* Draft.
* Generating.
* Ready for review.
* Approved.
* Scheduled.
* Published.
* Failed.
* Archived.

The user can:

* Approve.
* Reject.
* Request modifications.
* Edit manually.
* Reschedule.
* Publish immediately.

The user must be able to configure which content types require approval.

H. Publish content

The worker should publish using authorized integrations.

Where direct publishing is not supported:

* Create the content.
* Prepare the caption.
* Generate the appropriate media.
* Prepare a platform-specific publishing package.
* Notify the user to complete publication.

Do not simulate successful publishing when an API has only uploaded a draft.

Store the external post ID and publication result when available.

I. Audience engagement

This is a later extension of the first worker.

The architecture should support:

* Reading comments.
* Classifying questions.
* Identifying purchase intent.
* Drafting responses.
* Responding with authorization.
* Detecting potential leads.
* Escalating sensitive interactions.

Direct messages and public replies must have separate permissions.

Never allow the worker to make unsupported product claims, impersonate real customers or fabricate social proof.

J. Learn and optimize

Collect performance data from each connected platform.

Examples:

* Impressions.
* Views.
* Reach.
* Watch time.
* Average retention.
* Engagement.
* Likes.
* Comments.
* Shares.
* Saves.
* Profile visits.
* Link clicks.
* Leads.
* Conversions, when measurable.

The worker should compare performance across:

* Content topics.
* Hooks.
* Formats.
* Platforms.
* Publication times.
* Campaigns.
* Products.

It should generate insights and recommend experiments.

The system must distinguish correlation from demonstrated causation.

Do not claim that a particular content item generated sales unless the attribution data supports it.

7. Reporting and proactive behavior

Workers must not be limited to responding when users open the application.

They should operate according to a schedule and configured conditions.

7.1 Scheduled reports

Examples:

* Daily activity summary.
* Weekly content report.
* Monthly business performance.
* Campaign completion report.

7.2 Event-driven notifications

Examples:

* A scheduled publication failed.
* A video performs significantly better than average.
* A campaign is underperforming.
* A potential sales lead has been identified.
* An account has lost authorization.
* A product or campaign needs user approval.

7.3 Conditional automation

Users should be able to define rules such as:

“If a video reaches 10,000 views, notify me.”

“If engagement drops by 30% compared with the previous period, investigate and prepare recommendations.”

“If a customer expresses strong purchase intent, prepare a lead report.”

“Every Monday, prepare the week’s content plan.”

These rules should be implemented through a reusable event and automation system.

Avoid implementing separate cron logic for each worker type.

7.4 Notifications

Support:

* In-app notifications.
* Email, when configured.
* Future mobile push notifications.

All notifications should be linked to the relevant worker and task.

8. Technical architecture

The implementation must respect MEYA’s existing architecture.

Do not start from scratch.

The first task is to inspect the current repository, identify existing functionality and propose a refactoring plan.

Existing application components, avatar infrastructure, authentication, storage, database and AI integrations should be reused wherever possible.

8.1 Existing stack

The expected existing stack includes:

* Frontend: Vite + React + TypeScript.
* Backend: Supabase.
* Authentication: Supabase Auth.
* Database: Supabase PostgreSQL.
* Backend operations: Supabase Edge Functions.
* Media storage: Cloudflare R2, using the existing media infrastructure.
* Avatar rendering: existing Three.js / TypeScript avatar implementation.
* AI: existing OpenAI integrations.
* Deployment: existing frontend hosting infrastructure.

The development agent must verify the actual repository state rather than assume these components are all implemented identically.

Do not introduce Netlify Functions if the existing application uses Supabase Edge Functions.

Do not replace existing avatar rendering or media pipelines without a demonstrated technical reason.

8.2 Logical modules

Organize the implementation around these logical modules:

Worker Registry

* Creates workers.
* Stores configurations.
* Manages versions.
* Manages worker lifecycle.

Worker Generator

* Interprets user requests.
* Extracts business context.
* Recommends roles.
* Assembles configurations.
* Validates generated workers.

Identity Manager

* Manages visual identities.
* Manages voices.
* Manages personality.
* Manages avatar variants.

Role & Skill Registry

* Stores reusable roles.
* Stores reusable skills.
* Resolves skill dependencies.
* Supports versioning.

Tool & Connector Registry

* Manages integrations.
* Stores available capabilities.
* Manages authorization.
* Enforces permissions.

Memory Service

* Stores and retrieves worker memories.
* Separates business knowledge from learned memories.
* Supports retrieval and memory updates.

Execution Engine

* Runs tasks.
* Executes workflows.
* Tracks execution status.
* Handles failures and retries.
* Applies autonomy policies.

Scheduler & Event Engine

* Executes scheduled tasks.
* Processes relevant events.
* Triggers notifications and workflows.

Analytics Service

* Collects external metrics.
* Normalizes platform data.
* Calculates KPIs.
* Produces reports.

Worker UI

* Presents the avatar.
* Displays the worker’s state.
* Provides chat and controls.
* Displays activity and results.

These are logical boundaries, not instructions to create a separate microservice for every module.

Start with a modular architecture compatible with the existing application.

9. AI orchestration

The generator and the execution engine should be separate concepts.

The generator creates and configures workers.

The execution engine runs them.

9.1 Generator assistant

The generator assistant should:

1. Understand the user’s request.
2. Extract relevant business information.
3. Determine the appropriate role.
4. Recommend reusable skills.
5. Recommend tools.
6. Propose an identity and personality.
7. Define knowledge requirements.
8. Recommend objectives.
9. Recommend autonomy.
10. Generate a validated worker configuration.
11. Present the configuration for confirmation.
12. Create the worker after approval.

The assistant must be able to revise individual configuration components without recreating everything.

9.2 Runtime worker

At runtime, the worker receives:

* Current user instruction.
* Worker identity.
* Role definition.
* Relevant skills.
* Relevant knowledge.
* Retrieved memories.
* Available tools.
* Permissions.
* Current objectives.
* Task context.

It then decides whether to:

* Answer.
* Research.
* Generate content.
* Execute a workflow.
* Use a tool.
* Ask for clarification.
* Request approval.
* Escalate to the owner.

All external actions must be validated by the permission layer.

9.3 Execution trace

Every meaningful task must generate an execution record.

The user should be able to understand:

* What the worker was asked to do.
* What it decided to do.
* Which tools it used.
* Which actions succeeded.
* Which actions failed.
* Whether approval was required.
* What the result was.

This is essential for trust and debugging.

18. Final product principle

MEYA is not an avatar generator. It is a Digital Worker Generator.

The avatar is how humans see and interact with their digital workers.

The role determines what they do.

The skills determine what they can do.

The tools determine where they can act.

The memory determines what they learn and retain.

The objectives determine what they are trying to accomplish.

The autonomy and permission system determine what they are allowed to do.

The execution engine makes them productive.

Build this foundation once, and every new worker becomes a specialization of the same platform.
